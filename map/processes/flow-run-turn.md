# flow run turn

**Input:** `python -m cli.main flow run "<prompt>"` (optional `--session-id`, `--model`).
**Movement:** CLI builds an `AgentRunner`, which builds tools and a `PlanActFlow`; the flow loops states Planning, Critiquing, Premortem, PlanReview, Executing (one step per pass, with Updating and Reviewing as side exits), Verifying, Completed, persisting every emitted event.
**Output:** `AgentEvent`s streamed to the terminal; the `Session` row saved with the plan, events and final status.

## Steps
1. **CLI.** `_run_async` installs `ConsoleApproval` when stdin is a TTY (`cli/commands/flow.py:44-54`). `flow_run` (`:121`) builds the LLM through `_cli_llm`, which asks the container (`:127`, `:88-97`), takes state repo and `Mediator` from the shared container (`:128-129`, `:100-108`), and builds `AgentRunner` with `event_bus=_container.get(EventBusPort)` (`:131-140`).
2. **Session.** `AgentRunner.run_prompt` (`weebot/interfaces/cli/agent_runner.py:119`) loads the session if an id was given (`:137-138`), else (also for an unknown id) creates one and saves it (`:161-168`).
3. **Tools.** `_ensure_tools` calls `build_tools(role=self._role, ...)` once per runner (`agent_runner.py:91-96`, default role `"admin"` `:57`); see [mcp-tool-loading](mcp-tool-loading.md) for what goes in and [tool-call-guard-chain](tool-call-guard-chain.md) for the wrapping.
4. **Flow.** Without a router, `create_flow("plan_act", ...)` (`agent_runner.py:220-232`; with a router, `route_and_create_flow` `:192-218`). `create_flow` (`weebot/interfaces/factories.py:216`) delegates to `build_flow` (`factories.py:234`; `weebot/application/flows/flow_builder.py:82`) with `_cached` as the DI resolver (`factories.py:45-53`). `build_flow` fills a missing mediator and event bus from DI (`flow_builder.py:114-125`), resolves the optional collaborators (`:55-80, 126-165`) and builds `PlanActFlow` with `persistence_adapter=resolve("session_persistence")` (`:166-206`).
5. **Turn prologue.** `PlanActFlow.run` (`weebot/application/flows/plan_act_flow.py:334`) binds the session id to log records and seeds the cost meter (`:337-341`), then `_run_states` (`:345`) calls `begin_run` (`:346`, `weebot/application/flows/_run_prologue.py:26`): remember the original task (`_run_prologue.py:51-61`), extract session constraints when an extractor is wired (`:66-67`), hydrate behavioural rules (`:70-78`), resolve vague follow-ups with `ContinuationDetector` (`:80-82`), run `ToolAssembler.assemble` (`:85-96`; it returns the tools unchanged when no `mcp_bridge` is wired, `weebot/application/flows/collaborators/tool_assembler.py:53-54`, and `build_flow` passes none).
6. **Start state.** `FlowRouter.resolve_initial_state` (`_run_prologue.py:99-103`; `weebot/application/flows/flow_router.py:50`) tries, in order: a pending product gate (`flow_router.py:67-78`), a pending plan approval (`:80-114`), a pending user gate (`:115-194`), an incomplete last plan or a WAITING session with a plan (`:195-207`), else `PlanningState` (`:209-223`). An approve token or an empty reply on a pending plan, and the resume cases, give `ExecutingState`; the prologue saves the routed session and loads `session.get_last_plan()` (`_run_prologue.py:104-111`). For `PlanningState`, `ProductGateState` runs first when `PRODUCT_MODE_ENABLED` (`_run_prologue.py:126-133`; default off, `weebot/config/feature_flags.py:71`).
7. **Loop.** `while iteration_count <= max_iterations` (`plan_act_flow.py:377`). Each pass: a cross-process cancel marker sets the session FAILED, emits an `ErrorEvent` and breaks (`:379-383`, see [session-persistence](session-persistence.md)); termination conditions may hand the flow to `CompletedState(termination_reason=...)` (`:397-398`; `weebot/application/flows/collaborators/session_budget.py:95-118`); the session cost gate may do the same or pause the session WAITING (`plan_act_flow.py:401-407`; `session_budget.py:71-92`); then the state runs with the turn prompt (`plan_act_flow.py:433-445`). The loop breaks on session COMPLETED, WAITING or FAILED (`:472-476`) or flow status IDLE (`:479-480`); `PlanStuckError` ends the turn with an `ErrorEvent` (`:446-469`).
8. **Planning.** `PlanningState.execute` first asks Agent Workflow Memory for hints from a similar past workflow (`_awm_hints`, `weebot/application/flows/states/planning.py:347-370`, called at `:241`), then sends `CreatePlanCommand` with them, the session lessons and up to two past-failure notes (`similar_failure_notes`, `:214-227`) through the mediator (`:243-252`); a rejection sets the session FAILED (`:254-262`). Otherwise it emits and yields the reconstructed events and takes the plan from the CREATED `PlanEvent` (`:264-271`). No steps: `SummarizingState` (`:290-293`), then `MetaAnalysisState` (`weebot/application/flows/states/summarizing.py:55`), then `VerifyingState` (`weebot/application/flows/states/meta_analysis.py:96`). Otherwise the plan is snapshotted, optional DPPM runs, and the replanner is built with the same AWM hints (`planning.py:295-337`); the next state is `CritiquingState` when a critic is wired (`:339-342`), else `next_state_after_plan()` (`:345`).
9. **Critique and pre-mortem.** `CritiquingState` with no critic goes to `next_state_after_plan()` (`weebot/application/flows/states/critiquing.py:54-59`); a critique that is high, medium or did not run goes to `PremortemState`, a low-confidence one back to `PlanningState` (`:109-133`). `PremortemState` is skipped when the task preset disables it or the plan has fewer than `PREMORTEM_MIN_STEPS` steps (`weebot/application/flows/states/premortem.py:31, 45-57`), else it emits a `PlanEvent` carrying the risk notes (`:74-77`); it ends in `next_state_after_plan()` (`:90`).
10. **Plan review (pause).** `next_state_after_plan` returns `PlanReviewState` when `plan_review_enabled` (default true, `weebot/config/settings.py:391-395`), else `ExecutingState` (`weebot/application/flows/states/base.py:125-135`). A plan under `min_steps` is auto-approved (`weebot/application/flows/states/plan_review.py:73-80`). Otherwise the state emits `PlanReviewEvent` (`:87-91`), sets `plan_pending_approval` (`:94-96`) and WAITING (`:106`), writes the plan to an editable file (`:108-119`), saves the session directly (`:134-135`), emits the `WaitForUserEvent` (`:137-140`) and yields it (`:145`). The loop breaks on WAITING.
11. **Plan review (resume).** The CLI breaks on `WaitForUserEvent` (`cli/commands/flow.py:146-149`), reads an answer with `asyncio.to_thread(input)` (`:153-158`) and calls `runner.resume_session` (`:169`); EOF leaves the session WAITING (`:159-167`). `resume_session` requires WAITING (`agent_runner.py:279-282`), sanitizes and appends the answer, saves (`:285-294`), builds a new flow and runs it with the answer (`:297-310`). `FlowRouter` routes an approve token to `ExecutingState` after applying an edited plan file (`flow_router.py:94-100`, `_apply_plan_file` `:26-42`), anything else to `PlanningState` with the text as `_plan_modification_request` (`:102-114`).
12. **Executing (one step per pass).** `ExecutingState.execute` (`weebot/application/flows/states/executing.py:193`): no next step goes to `VerifyingState` (`:207-211`); an already COMPLETED step goes to `UpdatingState` (`:213-217`). `apply_pre_step_gates` (`:219`; `weebot/application/flows/states/_execution_gates.py:73-93`) runs, in order, the inbound-mail pause through `ExecApprovalPolicy` (`:96-121`), the constraint gate (`:124`), correction learning, steering (`:187`) and the repetition gate (`:205-222`, which sends a looping step to `VerifyingState`). No mediator goes to `UpdatingState` (`executing.py:227-236`). The step is marked RUNNING (`:240`) and `run_step_command` sends `ExecuteStepCommand` with the flow's `StepExecutionContext` (`:244`; `weebot/application/flows/states/_step_run.py:71-82`; context built at `plan_act_flow.py:605-614`).
13. **Step events.** `run_step_command` adds the step's token usage and skill gaps to the flow (`_step_run.py:89`; `plan_act_flow.py:616-620`), emits every reconstructed event (`_step_run.py:92-94`), flags a human pause on `WaitForUserEvent` or `ToolApprovalEvent` and records the pending approval (`:95-101`), and flags failure on `ErrorEvent` (`:103-104`).
14. **Step handler.** `ExecuteStepHandler.handle` reloads the session from the repo and takes the step from `get_last_plan()` (`weebot/application/cqrs/handlers/execute_step_handler.py:77-99`), builds an `ExecutorAgent` through the DI factory (`:102-106`; `weebot/application/di/__init__.py:579-591`, `step_executor` `:465-515`), delivers session constraints (`execute_step_handler.py:118-141`), and collects every event of `executor.execute_step` (`:144-148`).
15. **ExecutorAgent.execute_step** (`weebot/application/agents/executor/_base.py:456`): `prime_step` sets the step context on the tool executor and scopes tools (`weebot/application/agents/executor/_step_setup.py:36-59`). `_scope_tools_for` calls `select_tools(step.description, ...)` and `ToolCollection.set_visible` (`_base.py:435-454`; `weebot/application/services/tool_scope.py:106-119`; on by default, `WEEBOT_TOOL_SCOPE`, `weebot/config/feature_flags.py:279`). Hidden tools stay callable and are named in a system-prompt note (`weebot/application/agents/executor/_turn.py:111`; `weebot/application/models/tool_collection.py:167-174`). The loop runs `while self._step_budget.consume()` (`_base.py:495`); each turn calls `CascadeExecutor.call_with_cascade` (`_turn.py:54-56`; [model-cascade](model-cascade.md)), then runs the tool calls as a batch (`_base.py:549-554`; `ToolBatchRunner.run`, `weebot/application/agents/executor/_tool_batch.py:114-130`; `weebot/application/agents/executor/_tool_executor.py:355`; [tool-call-guard-chain](tool-call-guard-chain.md)).
16. **Back in ExecutingState.** Events are yielded (`executing.py:245-246`); a rejected command goes to `UpdatingState` (`:248-251`); a human pause leaves the session WAITING (`:256-260`; `weebot/application/flows/states/_step_outcome.py:416-418`). A failed step first reports its candidate skills as a failed use (`record_skill_uses`), then goes through `route_failure`: one retry for a minor failure, `PlanningState` for a critical one, else `UpdatingState` (`executing.py:262-268`; `_step_outcome.py:110-162`). Then the quality gate (retry once with a hint, `executing.py:270`; `_step_outcome.py:207-239`), the progress gate (`UpdatingState` on failure, `executing.py:272`; `_step_outcome.py:242-285`) and the evidence gate (`executing.py:277-280`): `evidence_gate` asks `step_audit_service.audit_step`; on a gap the step is retried once, then marked UNVERIFIED and sent to `UpdatingState`, and a `PlanEvent` is emitted (`weebot/application/flows/states/evidence_gate.py:15-62`). Otherwise the step is marked COMPLETED (`executing.py:282`; `_step_outcome.py:288-294`), knowledge is absorbed (`executing.py:285`) and `next_transition` (`:286-288`; `_step_outcome.py:361-413`) picks the successor: stay put after `terminate` while steps remain, `VerifyingState` when the plan is done (`:371-396`), `ReviewingState` when a code reviewer is wired and the step is a code step (`:398-411`), else `ExecutingState` (`:413`); memory is compacted first (`:393`).
17. **Updating.** `UpdatingState` revises the remaining plan and returns to `ExecutingState` (`weebot/application/flows/states/updating.py:138, 252`).
18. **Reviewing.** With no reviewer it passes straight back to `ExecutingState` (`weebot/application/flows/states/reviewing.py:64-66`); at the retry cap it approves (`:70-77`); approved goes to `ExecutingState` (`:111-115`), revise emits an updated `PlanEvent` and goes to `ExecutingState` (`:117-157`), reject marks the step FAILED and goes to `UpdatingState` (`:159-164`).
19. **Verifying.** `VerifyingState.execute` skips to `CompletedState` when CoVe is off, no plan, or no completed step (`weebot/application/flows/states/verifying.py:66-91`); otherwise it runs the CoVe questions inside `WorkspaceIntegrityGuard.watch` (`:107-112`) and ends in `CompletedState` (`:227`).
20. **Completed.** `CompletedState.execute` judges the run by `Plan.outcome()` (`weebot/application/flows/states/completed.py:173-186`): SUCCEEDED stamps the plan COMPLETED; FAILED (a step failed) or INCOMPLETE (a step unverified or never run) stamp it FAILED. It emits that `PlanEvent` (`:208-212`), yields an `ErrorEvent` listing unfinished steps for INCOMPLETE (`:311-317`), sets the session COMPLETED or FAILED and saves it (`:318-320`), yields `DoneEvent` (`:327`), then scores the trajectory (`:329-340`) and spawns background jobs (`:478-535`).
21. **Persistence on every emit.** `PlanActFlow._emit` hands the event to `EventPublisher.emit` (`plan_act_flow.py:237-258`): truth binding, credential sanitization, `session.add_event`, bus publish plus domain events, then save (`weebot/application/flows/event_publisher.py:63-95`); see [session-persistence](session-persistence.md).
22. **Epilogue.** `AgentRunner` publishes each yielded event the flow had not already emitted (`agent_runner.py:243-244`), takes the flow's session (`:247-251`), keeps COMPLETED, WAITING or FAILED and turns any other status into WAITING (`settled_status`, `:33-39`, `:253`) and saves (`:255`). `_run_async` drains background tasks, closes the MCP toolkit and the DB pools (`cli/commands/flow.py:58-73`).

Consequences (read from source, not run):
- A termination condition does not skip `CompletedState`: it sets it with the reason and the state runs on the same pass (`session_budget.py:111-117`; `completed.py:169-170`). Since R06 the session ends FAILED unless `Plan.outcome()` is SUCCEEDED (`completed.py:173-186, 318`), so a turn cut short by a cap with steps still pending ends FAILED (INCOMPLETE), not COMPLETED.
- `--model` reaches the planner command (`planning.py:247`), the step command (`_step_run.py:75`) and, as `pinned_model`, the executor's cascade, which tries it first (`plan_act_flow.py:605-614`; `weebot/application/models/step_execution_context.py:31`; `_base.py:182`; `weebot/application/agents/executor/_cascade.py:600`).
- The step handler reads the plan from the database (`execute_step_handler.py:77-83`), not from the flow; the prologue saves the routed session, with any applied plan-file edit, before the first step (`_run_prologue.py:104-108`).
