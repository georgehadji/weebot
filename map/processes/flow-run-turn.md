# flow run turn

**Input:** `python -m cli.main flow run "<prompt>"` (optional `--session-id`, `--model`).
**Movement:** CLI builds an `AgentRunner`, which builds tools and a `PlanActFlow`; the flow loops states Planning, Critiquing, Premortem, PlanReview, Executing (one step per pass, with Updating and Reviewing as side exits), Verifying, Completed, persisting every emitted event.
**Output:** `AgentEvent`s streamed to the terminal; the `Session` row saved with the plan, events and final status.

## Steps
1. **CLI.** `_run_async` installs `ConsoleApproval` when stdin is a TTY (`cli/commands/flow.py:44-55`). `flow_run` (`:121`) builds the LLM through `_cli_llm`, which asks the container (`:127`, `:88-97`), takes state repo and `Mediator` from the shared container (`:128-129`, `:100-108`), and builds `AgentRunner` with `event_bus=_container.get(EventBusPort)` (`:131-140`).
2. **Session.** `AgentRunner.run_prompt` (`weebot/interfaces/cli/agent_runner.py:119`) loads the session if an id was given (`:137-138`), else (also for an unknown id) creates one and saves it (`:161-168`).
3. **Tools.** `_ensure_tools` calls `build_tools(role=self._role, ...)` once per runner (`agent_runner.py:91-96`, default role `"admin"` `:57`); see [mcp-tool-loading](mcp-tool-loading.md) for what goes in and [tool-call-guard-chain](tool-call-guard-chain.md) for the wrapping.
4. **Flow.** Without a router, `create_flow("plan_act", ...)` (`agent_runner.py:220-232`; with a router, `route_and_create_flow` `:192-205`). `create_flow` (`weebot/interfaces/factories.py:214`) delegates to `build_flow` (`factories.py:232`; `weebot/application/flows/flow_builder.py:55`) with `_cached` as the DI resolver (`factories.py:43-51`). `build_flow` fills a missing mediator and event bus from DI (`flow_builder.py:82-93`), resolves the optional collaborators (`:96-125, 148-159`) and builds `PlanActFlow` with `persistence_adapter=resolve("session_persistence")` (`:126-160`).
5. **Turn prologue.** `PlanActFlow.run` (`weebot/application/flows/plan_act_flow.py:336`) binds the session id to log records and seeds the cost meter (`:340-343`), then `_run_states` (`:347`): remember the original task (`:371-380`), extract session constraints when an extractor is wired (`:386-387`), hydrate behavioural rules (`:393-397`), resolve vague follow-ups with `ContinuationDetector` (`:400-402`), run `ToolAssembler.assemble` (`:405-416`; it returns the tools unchanged when no `mcp_bridge` is wired, `weebot/application/flows/collaborators/tool_assembler.py:53-54`, and `build_flow` passes none).
6. **Start state.** `FlowRouter.resolve_initial_state` (`plan_act_flow.py:419-423`; `weebot/application/flows/flow_router.py:50`) tries, in order: a pending product gate (`flow_router.py:69-79`), a pending plan approval (`:81-114`), a pending user gate (`:125-194`), an incomplete last plan or a WAITING session with a plan (`:196-207`), else `PlanningState` (`:213`). An approve token or an empty reply on a pending plan, and the resume cases, give `ExecutingState`; the flow saves the routed session and loads `session.get_last_plan()` (`plan_act_flow.py:424-431`). For `PlanningState`, `ProductGateState` runs first when `PRODUCT_MODE_ENABLED` (`plan_act_flow.py:446-451`; default off, `weebot/config/feature_flags.py:70`).
7. **Loop.** `while iteration_count <= max_iterations` (`plan_act_flow.py:493`). Each pass: a cross-process cancel marker sets the session FAILED, emits an `ErrorEvent` and breaks (`:495-499`, see [session-persistence](session-persistence.md)); termination conditions may hand the flow to `CompletedState(termination_reason=...)` (`:513-514`; `weebot/application/flows/collaborators/session_budget.py:95-118`); the session cost gate may do the same or pause the session WAITING (`plan_act_flow.py:516-522`; `session_budget.py:71-92`); then the state runs with the turn prompt (`plan_act_flow.py:549-561`). The loop breaks on session COMPLETED, WAITING or FAILED (`:589-592`) or flow status IDLE (`:595-596`); `PlanStuckError` ends the turn with an `ErrorEvent` (`:562-583`).
8. **Planning.** `PlanningState.execute` sends `CreatePlanCommand` through the mediator (`weebot/application/flows/states/planning.py:219-227`); a rejection sets the session FAILED (`:229-236`). Otherwise it emits and yields the reconstructed events and takes the plan from the CREATED `PlanEvent` (`:241-245`). No steps: `SummarizingState` (`:265-268`), then `MetaAnalysisState` (`weebot/application/flows/states/summarizing.py:55`), then `VerifyingState` (`weebot/application/flows/states/meta_analysis.py:96`). Otherwise the plan is snapshotted, optional DPPM and AWM hints run (`planning.py:270-324`), and the next state is `CritiquingState` when a critic is wired (`:335-337`), else `next_state_after_plan()` (`:338-340`).
9. **Critique and pre-mortem.** `CritiquingState` with no critic goes to `next_state_after_plan()` (`weebot/application/flows/states/critiquing.py:54-59`); a critique that is high, medium or did not run goes to `PremortemState`, a low-confidence one back to `PlanningState` (`:109-133`). `PremortemState` is skipped when the task preset disables it or the plan has fewer than `PREMORTEM_MIN_STEPS` steps (`weebot/application/flows/states/premortem.py:31, 45-57`), else it emits a `PlanEvent` carrying the risk notes (`:74-77`); it ends in `next_state_after_plan()` (`:90`).
10. **Plan review (pause).** `next_state_after_plan` returns `PlanReviewState` when `plan_review_enabled` (default true, `weebot/config/settings.py:375-379`), else `ExecutingState` (`weebot/application/flows/states/base.py:125-135`). A plan under `min_steps` is auto-approved (`weebot/application/flows/states/plan_review.py:74-81`). Otherwise the state emits `PlanReviewEvent` (`:87-91`), sets `plan_pending_approval` (`:93-96`) and WAITING (`:106`), writes the plan to an editable file (`:108-119`), saves the session directly (`:134-135`), emits the `WaitForUserEvent` (`:137-140`) and yields it (`:145`). The loop breaks on WAITING.
11. **Plan review (resume).** The CLI breaks on `WaitForUserEvent` (`cli/commands/flow.py:145-149`), reads an answer with `asyncio.to_thread(input)` (`:153-158`) and calls `runner.resume_session` (`:169`); EOF leaves the session WAITING (`:159-167`). `resume_session` requires WAITING (`agent_runner.py:279-282`), sanitizes and appends the answer, saves (`:284-294`), builds a new flow and runs it with the answer (`:297-310`). `FlowRouter` routes an approve token to `ExecutingState` after applying an edited plan file (`flow_router.py:94-100`, `_apply_plan_file` `:26-43`), anything else to `PlanningState` with the text as `_plan_modification_request` (`:102-114`).
12. **Executing (one step per pass).** `ExecutingState.execute` (`weebot/application/flows/states/executing.py:193`): no next step goes to `VerifyingState` (`:207-211`); an already COMPLETED step goes to `UpdatingState` (`:214-217`). `apply_pre_step_gates` (`:219`; `weebot/application/flows/states/_execution_gates.py:73-93`) runs, in order, the inbound-mail pause through `ExecApprovalPolicy` (`:96-121`), the constraint gate (`:124`), correction learning, steering (`:187`) and the repetition gate (`:205-222`, which sends a looping step to `VerifyingState`). No mediator goes to `UpdatingState` (`executing.py:226-236`). The step is marked RUNNING (`:240`) and `run_step_command` sends `ExecuteStepCommand` with the flow's `StepExecutionContext` (`:244`; `weebot/application/flows/states/_step_run.py:70-81`; context built at `plan_act_flow.py:721-730`).
13. **Step events.** `run_step_command` adds the step's token usage and skill gaps to the flow (`_step_run.py:88`; `plan_act_flow.py:732-736`), emits every reconstructed event (`_step_run.py:91-93`), flags a human pause on `WaitForUserEvent` or `ToolApprovalEvent` and records the pending approval (`:94-101`), and flags failure on `ErrorEvent` (`:102-103`).
14. **Step handler.** `ExecuteStepHandler.handle` reloads the session from the repo and takes the step from `get_last_plan()` (`weebot/application/cqrs/handlers/execute_step_handler.py:72-94`), builds an `ExecutorAgent` through the DI factory (`:96-101`; `weebot/application/di/__init__.py:557-569`, `step_executor` `:440-488`), delivers session constraints (`execute_step_handler.py:113-136`), and collects every event of `executor.execute_step` (`:139-143`).
15. **ExecutorAgent.execute_step** (`weebot/application/agents/executor/_base.py:529`): `prime_step` sets the step context on the tool executor and scopes tools (`weebot/application/agents/executor/_step_setup.py:36-59`). `_scope_tools_for` calls `select_tools(step.description, ...)` and `ToolCollection.set_visible` (`_base.py:508-527`; `weebot/application/services/tool_scope.py:106-119`; on by default, `WEEBOT_TOOL_SCOPE`, `weebot/config/feature_flags.py:198`). Hidden tools stay callable and are named in a system-prompt note (`weebot/application/agents/executor/_turn.py:111`; `weebot/application/models/tool_collection.py:167-174`). The loop runs `while self._step_budget.consume()` (`_base.py:568`); each turn calls `CascadeExecutor.call_with_cascade` (`_turn.py:54-56`; [model-cascade](model-cascade.md)), then runs the tool calls as a batch (`_base.py:616-622`; `weebot/application/agents/executor/_tool_executor.py:318`; [tool-call-guard-chain](tool-call-guard-chain.md)).
16. **Back in ExecutingState.** Events are yielded (`executing.py:245-246`); a rejected command goes to `UpdatingState` (`:248-251`); a human pause leaves the session WAITING (`:256-260`; `weebot/application/flows/states/_step_outcome.py:373-375`). A failed step goes through `route_failure`: one retry for a minor failure, `PlanningState` for a critical one, else `UpdatingState` (`executing.py:262-265`; `_step_outcome.py:93-123`). Then the quality gate (retry once with a hint, `executing.py:267`; `_step_outcome.py:169-201`), the progress gate (`UpdatingState` on failure, `executing.py:269`; `_step_outcome.py:204-243`) and the evidence gate (`executing.py:274-277`): `evidence_gate` asks `step_audit_service.audit_step`; on a gap the step is retried once, then marked UNVERIFIED and sent to `UpdatingState`, and a `PlanEvent` is emitted (`weebot/application/flows/states/evidence_gate.py:15-62`). Otherwise the step is marked COMPLETED (`executing.py:279`; `_step_outcome.py:246-251`), knowledge is absorbed (`executing.py:281`) and `next_transition` (`:282-284`; `_step_outcome.py:318-370`) picks the successor: stay put after `terminate` while steps remain, `VerifyingState` when the plan is done (`:343-354`), `ReviewingState` when a code reviewer is wired and the step is a code step (`:356-368`), else `ExecutingState` (`:370`); memory is compacted first (`:350`).
17. **Updating.** `UpdatingState` revises the remaining plan and returns to `ExecutingState` (`weebot/application/flows/states/updating.py:138, 251-252`).
18. **Reviewing.** With no reviewer it passes straight back to `ExecutingState` (`weebot/application/flows/states/reviewing.py:64-67`); at the retry cap it approves (`:70-77`); approved goes to `ExecutingState` (`:111-115`), revise emits an updated `PlanEvent` and goes to `ExecutingState` (`:117-157`), reject marks the step FAILED and goes to `UpdatingState` (`:159-164`).
19. **Verifying.** `VerifyingState.execute` skips to `CompletedState` when CoVe is off, no plan, or no completed step (`weebot/application/flows/states/verifying.py:66-93`); otherwise it runs the CoVe questions inside `WorkspaceIntegrityGuard.watch` (`:104-112`) and ends in `CompletedState` (`:228`).
20. **Completed.** `CompletedState.execute` stamps the plan FAILED if any step failed, else COMPLETED (`weebot/application/flows/states/completed.py:174-178`), emits that `PlanEvent` (`:199-201`), sets the session COMPLETED or FAILED and saves it (`:292-295`), yields `DoneEvent` (`:302`), then scores the trajectory (`:304-315`) and spawns background jobs (`:433-489`).
21. **Persistence on every emit.** `PlanActFlow._emit` hands the event to `EventPublisher.emit` (`plan_act_flow.py:241-260`): truth binding, credential sanitization, `session.add_event`, bus publish plus domain events, then save (`weebot/application/flows/event_publisher.py:63-93`); see [session-persistence](session-persistence.md).
22. **Epilogue.** `AgentRunner` publishes each yielded event the flow had not already emitted (`agent_runner.py:243-244`), takes the flow's session (`:247-251`), keeps COMPLETED, WAITING or FAILED and turns any other status into WAITING (`settled_status`, `:33-39`, `:253`) and saves (`:255`). `_run_async` drains background tasks, closes the MCP toolkit and the DB pools (`cli/commands/flow.py:58-73`).

Consequences (read from source, not run):
- A termination condition does not skip `CompletedState`: it sets it with the reason and the state runs on the same pass (`session_budget.py:113-117`; `completed.py:168-169`). The session ends FAILED only when a step FAILED (`completed.py:174-178, 292`), so a turn cut short by a cap with steps still pending ends COMPLETED.
- `--model` reaches the planner command (`planning.py:223`), the step command (`_step_run.py:74`) and, as `pinned_model`, the executor's cascade, which tries it first (`plan_act_flow.py:728`; `weebot/application/models/step_execution_context.py:31`; `_base.py:258`; `weebot/application/agents/executor/_cascade.py:597`).
- The step handler reads the plan from the database (`execute_step_handler.py:72-78`), not from the flow; the flow saves the routed session, with any applied plan-file edit, before the first step (`plan_act_flow.py:424-428`).
